# seamless-fs (`sfs`) の仕様

カレントディレクトリのファイルを HTTP で配り、リレー(`seamless-fs-relay`、Cloudflare Worker)を通して、他の `sfs` サーバーのファイルも一覧に出す。他サーバーのファイルのリンクは、そのサーバーを指す(中継はしない)。

## 設定(環境変数。カレントの `.env` が優先)

| 名前 | 意味 |
|---|---|
| `HOST` / `PORT` | 待ち受けるアドレス |
| `WORKERS` | ワーカー数(1以上) |
| `ORIGIN` | 他のサーバーとリレーから、このサーバーに届くアドレス(http / https)。リレーの `SERVERS` に書いたものと同じアドレスにする |
| `RELAY_URL` | リレーのアドレス(http / https。https を推奨。http が localhost 以外だと警告) |
| `RELAY_PUBLIC_KEY` | リレーの公開鍵(base64url)。リレーからの呼び出しの署名を確かめる |
| `TOKEN` | **このサーバーだけ**のトークン(32文字以上。`sfs token` で作る) |

設定に誤りがあると、起動時にそれを書いて終了する。

## 秘密の作り方(サブコマンド。設定は要らない)

- `sfs token`: 新しいトークン(`TOKEN=...`)と、その SHA-256(`SHA256=...`)を出す。トークンはこのサーバーの `.env` に、SHA-256 はリレーの `SERVERS` に。
- `sfs hash`: 標準入力のトークンの SHA-256 を出す。
- `sfs keygen`: リレーの鍵の組を出す。`RELAY_PRIVATE_KEY` はリレーだけ(secret)、`RELAY_PUBLIC_KEY` はリレーと全サーバーに。

## 動作

1. 起動時: リレーに「このサーバーは消えた」を送ってから(前回の残りを消す)、ファイル一覧を `PUT <RELAY_URL>?first=true` で送る。`first` は、リレーが他サーバーのファイルを返すための印。
2. 実行中: カレントディレクトリ以下の変化を見て、変化があれば10秒おきに一覧を送り直す(隠しファイルだけの変化は無視)。
3. 停止(Ctrl-C、Unix では SIGTERM も): リレーに `DELETE` を送ってから止まる。
4. リレーからの `PUT /` で、他サーバーの一覧(`{origin, files}`)を受け取って入れ替える。`DELETE /` で消す。どちらも**リレーの署名**が正しいときだけ(違えば 401)。署名は、メソッド・このサーバーのアドレス・時刻・本文の SHA-256 に対する Ed25519。時刻が60秒以上ずれたものは受けない(サーバーの時計を合わせておく)。ほかのサーバー宛ての呼び出しは使い回せない。自分自身の一覧は無視する。

サーバー → リレーの呼び出しには `Authorization: Bearer <TOKEN>` を付ける。リレーは SHA-256 だけを持ち、この TOKEN の持ち主のアドレス以外の `origin` は受け付けない(403)。リレーの仕様は seamless-fs-relay の `docs/SPEC.md`。

通信の本文(JSON)の形は、以前と同じ。ファイル1件: `{origin?, parent, url?, name, size}`。`parent` は `/a/b/` の形。

## 配るもの・出すもの

- ファイルとディレクトリ一覧。`.` で始まる名前(と、その下)は、配らず、一覧にも出さず、リレーにも教えない。
- ルートの外を指すシンボリックリンクは、配らず、一覧にも出さない。
- 一覧のページは `Content-Security-Policy` でスクリプトを許さない。全レスポンスに `X-Content-Type-Options: nosniff`。

## 他サーバーから受け取るもの(信用しない)

- `origin` と `url` は http / https の URL だけ。ほかの形式(`javascript:` など)のファイルは捨てる。
- 名前に `/` や制御文字、ディレクトリに `..` や `\` があるファイルは捨てる。
- 受け取る数に上限: リクエスト本体 500 KB、1サーバーあたり 20,000 ファイル、256 サーバー(超えると 413)。
- 同じ名前のフォルダが複数のサーバーにあるときは、`origin` の文字順で最初のサーバーを指す(順序が毎回変わらない)。このサーバーに同名のフォルダがあれば、そちらを出す。

## 構成(`src/`)

`main`(起動)、`cli`(秘密を作るサブコマンド)、`config`(設定)、`confine`(配る範囲の制限)、`keys`(トークンと鍵)、`relay_auth`(リレーの署名の検査)、`model`(やりとりする形と検査)、`registry`(他サーバーのファイル。ディレクトリごとの索引)、`api`(リレーからの呼び出し)、`listing`(一覧ページ)、`scan` / `sync` / `relay`(リレーへの通知)。

## ビルド

`cargo build --release`(実行ファイル名 `sfs`)、`cargo test`。

## セキュリティ上の注意

- `TOKEN` はサーバーごと。漏れたら、そのサーバーの `TOKEN` を作り直し、リレーの `SERVERS` のハッシュを替える(ほかのサーバーは変えなくてよい)。
- リレーの秘密鍵が漏れたら、`sfs keygen` で作り直し、リレーと全サーバーの公開鍵を替える。サーバーの設定やトークンからは、リレーの署名は作れない。
- リレーが持つのはトークンの SHA-256 だけ。ただし `SERVERS` は公開のリポジトリに置きやすいので、トークンは必ず `sfs token` で作った長いもの(短い・推測できるトークンは、ハッシュから割り出される)。
- 配るのはカレントディレクトリ全体。秘密のファイルは置かないか、`.` で始まる名前にする。
- リレーが呼ぶのは、リレーの `SERVERS` にあるアドレスだけ。サーバーを足すときは `SERVERS` を書き換える。
- 他のサーバーのファイルは、リレーを信用して一覧に出す(リンクは、そのサーバーのアドレスを指す)。信用できないサーバーを `SERVERS` に入れない。
